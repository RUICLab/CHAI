How cheap must a server query be before server forecasting pays for itself?

    PYTHONPATH=. python3 -m adaptive.radio_sweep

Sensitivity analysis, not a campaign. One solar recording, 295 s of a 300 s
capture so nothing loops.

SCOPE, stated before the numbers. This measures ONE architecture: a server query
per decision period. It is not a statement about server-assisted design in
general -- batching several periods into one query, triggering queries only on
unusual conditions, or piggybacking the forecast onto traffic the device already
sends would all amortise the cost differently and are untested here.

LATENCY IS MODELLED AS ZERO. The device asks and the answer is available
immediately, with no packet loss and no retransmission. Every number here is
therefore OPTIMISTIC for the server; real latency and retries can only move the
break-even cost lower.

PREDECLARED READING OF THE BREAK-EVEN COST, fixed before running:

    above 200 uJ      a conventional low-power radio is viable
    10 - 200 uJ       only a cheaper or amortised communication design is plausible
    below 10 uJ       specialised backscatter or piggybacking is required
    no break-even     server forecasting offers no efficiency value in that cell

Reported per benchmark and deadline: per-offered efficiency, in-bound completion,
radio energy actually spent, number of queries, and the break-even cost against
both baselines.
